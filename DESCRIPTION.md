# Биржевой аналитик — описание решения

**Прототип:** https://uzex-ten.vercel.app (веб-чат, без регистрации)

## Идея
Ответ на вопрос о данных должен быть *посчитан*, а не сгенерирован. Поэтому LLM не «знает» ответ: она выбирает фильтры и пишет SQL, а числа, компании и даты берутся только из результата запроса к реестру. Отдельный программный валидатор не выпускает ответ, в котором есть хоть одно значение, которого нет в результатах запросов.

## Архитектура
Вопрос (RU / UZ-латиница / UZ-кириллица) → агент на **Gemini** (function calling) → инструменты:
1. `lookup` — нечёткий поиск товара, компании (имя или ИНН), региона, брокера с транслитерацией кириллица↔латиница (rapidfuzz). Возвращает точные ключи для фильтров.
2. `run_sql` — один read-only SELECT к **DuckDB** в памяти (500 000 сделок, ответ за миллисекунды), таймаут 8 с, внешний доступ к файлам отключён.
3. `submit_answer` — финальный ответ + допущения + флаг «нет данных».

→ **валидатор** → ответ + блок «На чём основано» (условия, SQL, строки результата).

## Подготовка данных
Исходные CSV нормализованы один раз в Parquet (`build/build_data.py`):
- суммы из текста с пробелами → числа, даты → DATE;
- `объём = количество × лот`, цена за единицу, **перевод экспортных USD-сделок в сумы по курсу на дату сделки**;
- **регионы**: в сделках — по-узбекски, в контрактах — по-русски; сведены в единый справочник с вариантами написания;
- **товары**: один товар записан продавцами по-разному («Хлопок-сырец» / «Хлопок сырец», «1 сорт» / «1-сорта» / «I сорт» / «первый сорт»). Склеены по коду ТН ВЭД, сорт и класс нормализованы отдельными полями;
- флаги статусов: аннулированная сделка считается несостоявшейся;
- контроль качества: 0 пропусков при сопоставлении сделок с контрактами, компаниями, брокерами, регионами и курсом.

## Защита от выдумок
- Промпт: все числа — только из SQL, вся арифметика (доли, суммы, средние) — внутри SQL; нет данных → честное «нет данных».
- Программная проверка каждого ответа: каждое число (с учётом «млн/млрд/трлн», округления, процентов), каждая дата и каждое название компании или брокера должны присутствовать в результатах инструментов. Не прошло — модель получает список расхождений и исправляет ответ. Не прошло снова — показывается только таблица результата запроса, без текста модели.
- Период вне 03.01.2022–30.10.2026, несуществующий товар/ИНН, пустой результат → «нет данных».
- Ответ на языке и в письменности вопроса.

## Как проверяли
- **Эталонный набор: 36 вопросов** (20 RU, 7 UZ-латиница, 4 UZ-кириллица; из них 6 — вопросы без ответа в данных). Эталоны посчитаны SQL напрямую, независимо от агента (`eval/build_expected.py`).
- В набор специально включены ловушки: бензин продаётся и в тоннах, и в литрах; аннулированные сделки; экспорт в долларах; частичная поставка; «Ташкент» город и область; ноябрь 2026 и 2021 год; несуществующий ИНН; вопрос «кто директор» (в данных нет).
- Автоматический прогон через боевую ссылку с оценкой: верно / верно при альтернативном допущении / ошибка, плюс время ответа (`eval/run_eval.py`).
- Запросы к модели с детальной трассировкой (время, токены, ошибки каждого шага). Это помогло найти перегрузку одной из моделей Gemini и переключиться на стабильную с автоматическим резервом.

## Технологии
Python, FastAPI, DuckDB, Parquet, Google Gemini (function calling), rapidfuzz, Vercel (serverless).

## Результаты прогона (боевая ссылка, 05.11.2026)
- **36 / 36 верных ответов** (включая 6 из 6 «нет данных»: ноябрь 2026, 2021 и 2030 годы, айфоны, несуществующий ИНН, директор компании).
- **0 выдуманных значений**: все 36 ответов прошли программную проверку по результатам запросов.
- Время ответа: медиана 8 с, максимум 15,6 с при лимите 90 с.
- Узбекский язык: 11 вопросов (латиница и кириллица), все ответы даны на языке и в письменности вопроса.
